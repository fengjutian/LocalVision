# LocalVision 产品与技术规格

- 文档版本：2.0
- 产品版本：0.1.0
- 更新日期：2026-10-13
- 状态：MVP 开发中

## 1. 产品决策摘要

LocalVision 是 Android 端侧视觉分析应用，也是可复用的模型运行容器。首发体验面向普通用户，工程能力同时服务模型开发者。默认本地处理、能力来源透明、没有真实模型时绝不展示模拟结果。

北极星指标是“成功完成一次有用的本地分析的用户占比”。首轮验证指标：图片选择成功率 ≥ 99%；已支持设备上的无崩溃分析完成率 ≥ 98%；核心任务结果有用率（用户评价）≥ 70%；7 日内二次使用率 ≥ 20%。这些是验证目标，不是当前承诺。

## 2. 用户问题与价值主张

用户需要在不上传私人照片的前提下，快速知道图片中是否有人脸、人体姿态或店铺信息。开发者需要以统一契约替换模型，而不重写页面、调度与结果渲染。LocalVision 提供：

1. 默认离线：选图、预处理、推理与展示均在设备内完成。
2. 可信结果：显示模型、版本、许可证、置信度、耗时和适用限制。
3. 可扩展：任务接口、运行时和 UI 解耦，新增模型通过注册表与适配器接入。
4. 可审计：模型权重、来源、哈希、数据集版本和评估报告一一关联。

## 3. 范围与版本

### 0.1.0 工程基线（本仓库已实现）

- Android Compose 单应用工程；最低 Android 8.0（API 26）。
- 系统文件选择器选择单张图片，不申请相册全量读取权限。
- 人脸检测、人体姿态、店铺分析三种任务切换。
- 模型注册表、统一结果类型、归一化坐标与视口映射。
- Idle、Running、Success、Error 和取消状态。
- 模型尚未接入时显示真实状态和可操作错误，不产生模拟结果。
- 坐标映射与模型注册表单元测试。

### 0.2.0 人脸检测 MVP

- 基线模型确定为 OpenCV Zoo `face_detection_yunet_2023mar.onnx`（FP32），运行时为 ONNX Runtime Android，首发执行后端为 CPU。
- 支持多人、无脸、侧脸和遮挡样例；结果包括框、置信度与数量。
- 输出五个人脸关键点（双眼、鼻尖、双侧嘴角）；不输出身份、人脸特征或敏感属性。
- 记录解码、预处理、推理、后处理耗时。
- 独立测试集给出 Precision、Recall、mAP；报告按脸尺寸与场景切片。
- 明确排除身份识别、特征库、年龄/性别/种族等敏感推断。
- FP32 通过验收后再比较 YuNet INT8；NNAPI 仅作为实验后端，不作为首发默认后端。

### 0.3.0 姿态 MVP

- 输出关键点、单点置信度和骨架；低置信度关键点不连线。
- 单图只表述静态姿态，不宣称识别连续动作或跌倒事件。
- 使用关键点 AP/PCK、耗时与内存峰值验收。

### 0.4.0 店铺 MVP

- 拆成门面检测、类别分类、招牌 OCR 三个独立能力，可分别缺省。
- 结构化输出位置、类别、文本、置信度和各子任务模型来源。
- OCR 文本不等同于经营主体、品牌归属、营业状态或地理位置。

## 4. 核心用户故事与验收

### US-01 选择图片

作为用户，我可以通过系统选择器选择图片并看到预览，以便确认分析对象。

验收：不申请广泛存储权限；取消选择后状态不变；损坏或不可读 URI 给出错误；切换图片会取消进行中的任务并清空旧结果。

### US-02 选择任务并分析

作为用户，我可以选择一个已安装能力并开始本地分析。

验收：未选图时按钮禁用；任务切换清空旧结果；同一时刻每个页面最多一个分析任务；可取消；无模型时清楚告知而非崩溃或假结果。

### US-03 理解结果

作为用户，我能看到检测框/关键点/文字、置信度与耗时，并理解限制。

验收：叠加层与 `ContentScale.Fit` 后图像坐标一致；低置信度视觉弱化；空结果与错误结果严格区分；显示模型名、版本和许可证。

### US-04 隐私控制

作为用户，我知道图片在哪里处理并能删除可选历史与模型缓存。

验收：默认无网络调用；日志不含 URI、图片字节、OCR 全文或人脸特征；云端功能必须二次确认并单独披露服务方与保留策略。

## 5. 体验与状态设计

主流程：选择图片 → 选择任务 → 检查模型 → 本地分析 → 叠加结果 → 查看详情。页面必须覆盖空白、已选图、模型缺失、加载中、成功无目标、成功有目标、用户取消、图片错误、模型错误和内存不足状态。

置信度是模型输出分数，不等于事实概率。界面使用“模型置信度”表述，并允许任务配置展示阈值。低于阈值的候选默认不显示，但在开发者模式可检查。

无障碍要求：触控目标至少 48dp；不只靠颜色表达状态；叠加标签有高对比背景；重要结果提供文本列表；支持系统字体缩放。

## 7. 非功能要求

性能基线必须绑定设备、图片尺寸和模型版本。首个目标测试集：低端/中端/带 NPU 的 ARM64 设备各至少一台；输入长边 1280px；预热后 P50/P95 延迟、峰值 PSS、连续 30 次温升分别记录。0.2.0 发布门槛建议为中端机 P95 ≤ 800ms、峰值增量内存 ≤ 250MB，实测后调整。

可靠性：模型加载与执行在 IO/Default 调度器；任务随 ViewModel 生命周期取消；OOM 前先按上限采样图片；模型损坏返回可恢复错误；空检测是合法成功结果。

安全：模型清单使用固定 schema；仅加载应用私有目录；下载包校验 SHA-256，正式版增加签名校验；禁止在 APK 放置长期云端密钥；服务端响应做大小、类型、范围校验。

## 8. 架构契约

```text
Compose UI → MainViewModel → VisionEngine
                              ├─ ModelRegistry
                              ├─ ImagePreprocessor
                              ├─ RuntimeAdapter (ONNX/LiteRT/MediaPipe)
                              └─ TaskPostprocessor
                                      ↓
                           typed VisionResult
```

`VisionTask` 表示用户意图；`ModelDescriptor` 表示可审计模型；`VisionEngine` 是任务执行边界；所有空间结果使用 `[0,1]` 原图归一化坐标，UI 最后一跳映射到视口。运行时原始 Tensor 不得穿透到 UI。

模型清单后续字段：schemaVersion、modelId、version、task、runtime、asset、sha256、license、source、minimumAppVersion、input、outputs、normalization、thresholds、labels、limitations。未知主版本拒绝加载，未知可选字段忽略。

### 8.1 人脸检测实现契约（已批准）

决策日期为 2026-10-13。0.2.0 使用 YuNet FP32 建立正确性与性能基线，不同时引入第二套推理框架。

实现必须满足：

1. 使用固定版本的 `com.microsoft.onnxruntime:onnxruntime-android`，禁止使用 `latest.release`。
2. `OrtEnvironment` 在进程内复用；同一模型的 `OrtSession` 复用并由模型生命周期统一关闭。
3. 图片解码需处理 EXIF 方向，并在进入模型前限制最大尺寸，避免超大图造成内存峰值。
4. `YuNetPreprocessor` 明确定义输入尺寸、缩放/填充方式、通道顺序、数值类型与归一化参数，禁止依赖隐式默认值。
5. `YuNetPostprocessor` 负责输出维度校验、置信度阈值、NMS、人脸框和五点关键点解析；异常 Tensor 必须返回可理解的模型错误。
6. 后处理结果统一转换为基于已校正原图的 `[0,1]` 坐标，不允许把模型输入坐标直接交给 UI。
7. `OnnxFaceDetectionEngine` 通过现有 `VisionEngine` 接口返回类型化结果；ONNX Tensor、Session 或厂商类型不得泄漏到 UI 层。
8. 推理支持协程取消；所有 `OnnxTensor`、`OrtSession.Result` 等原生资源使用确定性关闭。
9. 默认仅使用 CPU Execution Provider。NNAPI 必须通过功能一致性和目标真机基准后才能作为可选配置开放。
10. 未加载模型、模型哈希不符、输入不可读、输出契约不符、推理取消和内存不足必须区分错误类型。

推荐代码边界：

```text
FaceDetectionEngine
  ├─ ImageDecoder / ExifNormalizer
  ├─ YuNetPreprocessor
  ├─ OnnxRuntimeSession
  ├─ YuNetPostprocessor
  └─ FaceResultMapper
```

模型文件默认随应用发布，使首次运行无需联网。未来模型下载功能上线后，仍必须先完成哈希、签名和兼容性校验，再原子切换活动版本。

## 9. 模型准入门禁

候选模型只有同时通过以下检查才能合入：来源 URL 与提交版本固定；权重和代码许可证允许目标商业用途与再分发；输入输出契约可复现；ONNX 算子受移动运行时支持；数值一致性测试通过；独立测试集达到门槛；三档真机完成性能测试；生成 SHA-256 与模型卡。

模型卡必须包含用途、非用途、训练/评估数据来源、指标及切片、已知偏差、预处理、阈值、许可证、维护人和回滚版本。许可证不明确即视为不可发布。

### 9.1 YuNet 准入记录要求

合入模型权重的同一次变更必须提交以下记录，缺一不可：

- 模型来源：OpenCV Zoo 的 `models/face_detection_yunet/face_detection_yunet_2023mar.onnx`。
- 固定来源仓库的精确 commit SHA，不允许仅记录 `main` 分支。
- 对下载后的原始 ONNX 文件计算 SHA-256，并由构建或测试任务校验。
- 归档 YuNet 模型目录中的 MIT License；应用的第三方声明中保留版权和许可文本。
- 单独归档 ONNX Runtime 的许可证与第三方声明。仓库根许可证、模型权重许可证和运行时许可证不得混写为一项。
- 保存输入/输出节点名称、shape、dtype、预处理、阈值、NMS 参数和五点关键点顺序。
- 保存模型来源指标，同时明确它们不能替代 LocalVision 独立测试集结果。
- 记录审查人、审查日期、商业使用与再分发结论；正式商业发布前完成法务复核。

初始模型清单应使用如下逻辑标识；来源 commit、SHA-256 和运行时版本在实际引入文件时填写真实值：

```yaml
modelId: yunet-face-detection
version: 2023mar-fp32
task: FACE_DETECTION
format: ONNX
runtime: ONNX_RUNTIME_ANDROID
license: MIT
sourcePath: models/face_detection_yunet/face_detection_yunet_2023mar.onnx
commercialUseReview: pending-legal-review
redistributionReview: pending-legal-review
```

## 10. 测试策略

- 单元：缩放/裁剪/EXIF、Tensor 排布、NMS、阈值边界、坐标逆变换、关键点连接、OCR 解析、清单 schema。
- 契约：每个适配器用固定输入验证输出维度、范围和标签映射。
- 集成：选图到结果；配置变更；后台/恢复；连续切换；取消；损坏模型；超大图；无目标。
- 模型回归：固定金标集与困难样例集；比较质量指标和逐样例漂移。
- 真机：冷/热启动、P50/P95、PSS、30 次连续推理、耗电和温升。
- 隐私：离线抓包为零；日志扫描；备份配置；缓存清除；云端确认门禁。

### 10.1 YuNet 0.2.0 验收门槛

- 使用至少 100–300 张来源与授权可追溯的图片，覆盖单脸、多人、无人脸、小脸、侧脸、遮挡、暗光和旋转场景。
- 无人脸图片返回成功的空列表；模型错误不得伪装为空结果。
- 使用合成基准图验证框与五点关键点坐标，结果叠加误差不超过 2 px。
- 相同图片、相同模型和相同配置重复执行结果稳定。
- 单元测试覆盖预处理、输出 shape 校验、阈值边界、NMS、填充逆变换和关键点顺序。
- 中端目标机预热后 P95 推理以 500 ms 为优化目标，0.2.0 发布上限为 800 ms；峰值增量 PSS 不超过 250 MB。
- 连续运行 30 次无崩溃、无持续内存增长，并记录温升。
- FP32 完成全部验收后，INT8 才能进入对照测试；只有质量下降在批准范围内且目标设备确有收益时才可替换 FP32。
- NNAPI 必须逐设备记录回退情况、数值偏差与 P50/P95；不满足一致性时自动使用 CPU。

## 11. 数据与训练治理

数据集需记录来源、授权、采集时间、版本、标注规范、清洗记录、主体级去重和拆分策略、已知偏差。相同人物/门店/视频片段不得跨训练与测试集泄漏。每次训练固化随机种子、代码提交、环境锁文件、超参数和数据集版本。

训练链路：合法数据 → 清洗去重 → 标注质检 → 主体级拆分 → 基线 → 微调 → 独立测试 → ONNX 导出 → 数值一致性 → Android 真机 → 模型卡与签名 → 灰度发布。

## 12. 商业化验证

第一阶段不同时建设消费者订阅、SDK 和行业项目三条重路线。先通过 10–20 位目标用户访谈和可用 MVP 验证主要场景。事件统计默认只记录本地聚合计数；任何远程分析必须单独同意，且不得包含图片内容或稳定设备标识。

可能的付费假设：专业版提供批量分析、模型管理与报告；开发者版提供 SDK、基准测试与支持；企业版提供私有模型适配和离线部署。进入开发前分别验证频率、替代方案、预算与采购约束。

## 13. 交付路线与完成定义

每个版本只有满足“代码、测试、模型卡/许可证、真机报告、隐私检查、回滚方案、用户可理解的限制说明”才算完成。下一步顺序：

1. 完成 0.1.0 真机 UI 与图片解码测试。
2. 固定 YuNet 2023mar FP32 的来源 commit 与 SHA-256，归档模型 MIT License、ONNX Runtime 许可证和审查记录。
3. 固定 ONNX Runtime Android 版本，实现 CPU Session、YuNet 前处理、后处理和资源释放。
4. 实现人脸框、五点关键点、置信度、模型信息与分阶段耗时展示。
5. 建立小型、合法授权的独立评估集，固化质量与三档真机性能基线。
6. 完成 0.2.0 验收后，对比 INT8；NNAPI 保持实验状态。
7. 基于真实反馈决定姿态或店铺能力的先后顺序。

## 14. 当前已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型许可证不允许分发 | 无法商业发布 | 准入前审查，保留替换候选 |
| 移动端延迟/内存不达标 | 体验差或崩溃 | 先基准，再量化/裁剪/换模型 |
| 店铺定义过宽 | 指标与体验不可控 | 三个子任务独立验收 |
| 测试集泄漏 | 指标虚高 | 主体级拆分、独立测试集 |
| 将静态姿态误解为动作 | 误导用户 | 文案边界、时序模型另立项目 |
| 置信度被理解为事实概率 | 错误决策 | 明示含义，不做高风险自动决策 |
| 范围持续膨胀 | 延期 | 每版只交付一个可测增量 |
